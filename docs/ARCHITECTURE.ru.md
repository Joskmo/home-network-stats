# Архитектура

Это приложение для одного владельца, а не распределённая платформа. Основные
границы: браузер, HTTP-процесс дашборда, сборщики на домашнем сервере и Telegram-бот.
На роутер не устанавливаются Python или JavaScript. Исходники frontend — strict
TypeScript; JavaScript для браузера получается сборкой, а не редактируется отдельно.

## Ответственность компонентов

| Компонент | Отвечает за | Не должен отвечать за |
| --- | --- | --- |
| `frontend/shared/` | Типы HTTP/сессии, общие DOM-утилиты | Доступ к роутеру, постоянное хранение паролей |
| `frontend/topology/` | Модель карты, раскладку, наблюдения, редактор и отрисовку | Авторизацию, SSH, окончательное сохранение |
| Точки входа дашборда и безопасности | Статистику, формы входа и доверия | Проверку пароля и доказательство идентичности |
| `dashboard/web.py` | HTTP-маршруты, лимиты запросов, auth/CSRF, список разрешённых ресурсов | Разбор роутерных наблюдений |
| `dashboard/auth.py`, `dashboard/access.py` | Сессии, пароли, задержки, LAN-идентичность запроса | Доверие на основании карты сети |
| `dashboard/topology.py` | Валидацию и атомарное сохранение карты, ревизии, ICMP | Угадывание кабелей |
| `dashboard/discovery.py` | Read-only сбор и объединение устройств по MAC | Затирание ручных связей, выдачу прав доступа |
| `dashboard/inventory.py`, `dashboard/sampler.py` | Сбор идентичности и скорости WAN на сервере | Доверие к идентичности из браузера |
| `dashboard/data.py` | Чтение истории и скорости | Запись счётчиков, восстановление несуществующей истории |
| `main.py`, `app.py` | Запуск бота, цикл сбора, команды и суточный отчёт | HTTP-состояние дашборда |
| `collector.py`, `nlbw.py`, `devices.py` | Чтение и разбор счётчиков, DHCP-имена | Изменение настроек роутера |
| `history.py`, `reports.py`, `telegram_client.py` | Приращения трафика, диаграммы, отправку владельцу | Выдуманный трафик и произвольных получателей |

## Путь данных карты

Модули разделены по ответственности: `types.ts` — контракт карты; `domain.ts` —
преобразования графа; `layout.ts` — геометрия; `observations.ts` — трактовка
наблюдений; `rendering.ts` — отрисовка; `editor.ts` — формы; `controller.ts` —
активный черновик и жизненный цикл запросов; `i18n.ts` — словари двух языков.
Чистые модули не зависят от DOM или HTTP. Редактор и отрисовка общаются с
контроллером через типизированные callbacks. Общий `DashboardBridge` передаёт
трём входным сборкам текущие сессию/язык и типизированный HTTP API.

1. Сервер читает DHCP, таблицу MAC и Wi-Fi-ассоциации штатными командами через SSH.
2. Результат — наблюдения, а не готовая схема кабелей и не доказательство доступа.
3. Импорт объединяет устройства по MAC, сохраняя ручные имена, порты, связи и
   временно отсутствующие устройства.
4. Браузер редактирует черновик. Применение обнаружения не равнозначно сохранению.
5. Сохранение передаёт карту с ревизией. Backend проверяет её и атомарно записывает
   только при совпадении текущей ревизии, иначе возвращает конфликт.
6. ICMP присоединяется по ID и совпадающему IP; свежесть проверки учитывается отдельно.

Тип устройства и среда соединения заданы явно. **Wi-Fi — значок без линий.**
Обнаруженный LAN-порт показывает, через какой интерфейс доступен MAC: он не
доказывает ни наличие коммутатора, ни прямое подключение. Неуправляемый коммутатор
и его внутренние порты задаются пользователем.

## Визуальные принципы карты

Карта предназначена для наблюдения и осмотра, а не для постоянного отображения
всех подписей кабелей. Порты изображаются гнёздами на устройствах; связь крепится
к соответствующему гнезду. При наведении, фокусе с клавиатуры или касании
выделяется подключение, а имена концов и порты показываются крупно в отдельной
панели, не поверх линий. Обнаруженный интерфейс помечается как наблюдение, а не
подтверждённый разъём корпуса. Неизвестные порты и Wi-Fi-кабели не придумываются.

Референсы общих принципов взаимодействия, не зависимости проекта:
- [yFiles Network Monitoring](https://www.yfiles.com/demos/showcase/networkmonitoring/):
  различимые устройства, ненавязчивые связи, контекстные подробности.
- [React Flow handles](https://reactflow.dev/learn/customization/handles):
  несколько отдельных точек подключения на одном устройстве.

## Сборка и доставка

- Источник истины — `frontend/`, строгая проверка типов — `tsconfig.json`.
- Зависимости фиксирует `package-lock.json`, установка — `npm ci`.
- `npm run typecheck` проверяет типы; `npm run build` собирает ресурсы в
  `dashboard/static/`; `npm test` проверяет frontend-модель.
- Сгенерированные `app.js`, `topology.js`, `security.js` исключены из Git.
- Docker собирает TS в отдельной Node-стадии. В обслуживающем Python-контейнере
  Node/npm не запускаются.
- CI сначала собирает frontend, затем запускает Python-тесты и браузерные проверки
  с изолированными данными, включая настоящий HTTP, авторизацию и сохранение.

## Данные и границы доверия

Файловая система web-контейнера read-only, кроме существующих auth/topology mounts.
История, скорость и инвентарь подключены только для чтения. SSH-ключ остаётся на
хосте. Runtime `.env`, токены, состояние паролей, живая сеть и артефакты браузера
не публикуются в Git.

Удобный вход из LAN требует точного доверенного ingress и свежего независимого
инвентаря. Наличие устройства на карте не даёт ему доступ. Физическая схема,
DHCP, соседство и ответ ICMP — разные источники информации.

## Границы рефактора

Миграция на TS разделяет ответственность браузерного кода и делает сборку
воспроизводимой. Она не меняет Python HTTP API, не добавляет frontend-фреймворк,
не переносит историю, не расширяет доступ из LAN и не перекраивает пакеты бота
ради переименований. Backend сохраняет существующие проверенные границы модулей.
