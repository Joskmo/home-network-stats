# Home network stats

Telegram-бот для единственного владельца: Linux-сервер раз в пять минут читает счётчики OpenWrt `nlbwmon` по SSH, сохраняет измеренные приращения RX + TX по устройствам в SQLite и отправляет **круговые диаграммы**. Python на роутере не нужен. Существующий прокси используется без изменения настроек.

## Команды

- `/start`, `/help` — справка.
- `/today`, `/yesterday` — диаграмма измеренного трафика и покрытие периода.
- `/status` — время последнего успешного сбора и состояние сборщика.
- `/language ru`, `/language en` — выбор языка с сохранением после перезапуска; по умолчанию русский.

После 09:00 по **Europe/Moscow** бот отправляет отчёт за вчера. Дата успешной отправки сохраняется; при ошибке отправка повторяется. Строгой гарантии «ровно один раз» нет: сбой между приёмом фотографии Telegram и записью отметки в SQLite может привести к повтору. Пропущенные старые дни автоматически не рассылаются; после запуска отправляется только вчерашний отчёт.

## Ограничения учёта

Первый замер — только исходная точка: накопленные счётчики роутера не выдаются за собранную историю. Новые устройства и сброшенные счётчики требуют новой базы отсчёта. Интервалы длиннее 450 секунд и интервалы, пересекающие московскую полночь, исключаются: бот не придумывает распределение байтов во времени. Исчезнувшие устройства отмечаются. Корректные приращения других устройств могут сохраняться даже в неполном интервале.

**Суточные отчёты обычно неполные даже при исправном сборщике**, поскольку интервал через полночь исключён намеренно. Месячные суммы также являются нижней оценкой измеренного трафика, а не полным расчётом провайдера. История до установки не восстанавливается. При отсутствии данных выводится честное сообщение вместо ошибочной диаграммы. Видимость `nlbwmon` зависит от топологии, аппаратного ускорения и настроек роутера; локальная коммутация и биллинг провайдера могут отличаться. Диаграммы и история содержат приватные данные.

### Имена устройств

Штатный ash-скрипт `deploy/home-network-read` экспортирует только сведения об именах и адресах DHCP-клиентов. Установите его как `/usr/libexec/home-network-read` на OpenWrt с правом исполнения. Бот обновляет справочник при каждом сборе и сохраняет подписи в SQLite. Имена статических DHCP-привязок имеют приоритет перед именами текущих аренд; при отсутствии имени используется IP. Дашборд использует те же подписи, что и бот, но учёт устройств с одинаковыми именами остаётся раздельным по MAC. Неизвестным устройствам имена не придумываются; MAC можно посмотреть во всплывающей подсказке таблицы. Чтобы изменить подпись, переименуйте статическую DHCP-привязку в OpenWrt и дождитесь следующего сбора.

### Карта сети

В защищённом дашборде есть двуязычный редактор топологии: иконки типов устройств,
подписанные порты роутера/коммутатора, разные обозначения Ethernet и Wi-Fi,
авторазмещение и вставка неуправляемого коммутатора в разрыв кабеля. Автосбор
показывает наблюдаемые пути, но не придумывает физические соединения. Неизвестные
типы устройств и маркировку физических портов уточняйте вручную, затем сохраните
карту. Подробнее: [карта, ограничения обнаружения и развёртывание](deploy/TOPOLOGY.md).

### Разработка frontend

Исходники браузерной части — strict TypeScript в `frontend/`. Сгенерированные
`dashboard/static/*.js` вручную не редактируются. Границы компонентов описаны в
[архитектуре проекта](docs/ARCHITECTURE.ru.md).

```sh
npm ci
npm run build
npm test
python -m unittest discover -v
```

CI и стадия сборки Docker используют Node 22. В обслуживающем контейнере работает
только Python; Docker собирает frontend автоматически. Перед локальными
Python-тестами, проверяющими статические ресурсы, нужен `npm run build`.

## Установка

Нужны Linux, Python 3.11+, OpenSSH, пользовательский systemd, установленный `nlbwmon` на OpenWrt и уже работающий HTTP-прокси `http://127.0.0.1:10818` (в эталонном развёртывании — Mihomo). Telegram всегда использует этот адрес, не наследуя прокси из окружения. Сейчас адрес задан в `telegram_client.py`, отдельной переменной конфигурации нет.

1. Создайте бота через BotFather, отправьте ему `/start` из личного аккаунта владельца и узнайте положительный числовой ID этого аккаунта.
2. Разместите исходники на сервере. Пример пути: `/srv/self-hosted-music/traffic-telegram-bot`; при другом пути исправьте оба пути в unit-файле.
3. Создайте окружение, установите зависимости и выполните тесты:

   ```sh
   python3 -m venv .venv
   .venv/bin/python -m pip install -r requirements.txt
   .venv/bin/python -m unittest test_bot test_history test_reports test_localization test_telegram test_app test_runtime -v
   ```
4. Настройте отдельный SSH-ключ пользователя службы. Проверьте ключ хоста роутера независимым способом и сохраните в `~/.ssh/known_hosts`. Сборщик использует строгую проверку хоста, пакетный режим и только заданный ключ. По возможности ограничьте ключ командой `nlbw -c json -g mac`. Она читает данные из памяти: не добавляйте `commit` или Python на роутер и не удаляйте чужие ключи.
5. Создайте каталог `~/.config/home-network-stats/` с правами 0700. Токен храните отдельно в `telegram-token`, права 0600, владелец — пользователь службы. Скопируйте `deploy/runtime.env.example` в `~/.config/home-network-stats/runtime.env`, замените все шаблонные значения и установите 0600. Эти файлы нельзя коммитить. `TRAFFIC_DATA_DIR` — отдельный доступный для записи каталог 0700; внутри создаётся `traffic.sqlite3`.
6. До запуска службы проверьте реальные подключения:

   ```sh
   set -a
   . "$HOME/.config/home-network-stats/runtime.env"
   set +a
   .venv/bin/python main.py verify
   .venv/bin/python main.py collect-once
   # Дождитесь второго реального замера: первый — лишь база отсчёта.
   .venv/bin/python main.py send-today
   ```

   `verify` выполняет `getMe`, `getChat` через прокси и читает роутер. `send-today` действительно отправляет фото владельцу. Пока служба работает, блокировка не позволяет параллельно запускать эти команды.
7. Установите пользовательскую службу:

   ```sh
   mkdir -p ~/.config/systemd/user
   cp deploy/home-network-stats.service ~/.config/systemd/user/
   systemctl --user daemon-reload
   systemctl --user enable --now home-network-stats.service
   systemctl --user is-active home-network-stats.service
   journalctl --user -u home-network-stats.service -n 20 --no-pager
   loginctl show-user "$USER" -p Linger
   ```

   Для работы после загрузки без входа пользователя администратору может потребоваться `loginctl enable-linger SERVICE_USER`. Проверяйте несколько последовательных сообщений `Collection succeeded`, а не только состояние процесса. Служба перезапускается при сбое и не меняет роутер или прокси.

## Безопасность и обслуживание

Проверяются одновременно ID отправителя и ID личного чата. Группы, сообщения от имени каналов и другие пользователи не могут изменить получателя: все отправки адресованы только настроенному владельцу. Язык, смещение обновлений, дата суточной отправки и ID последней фотографии сохраняются в SQLite. Токены, реальный ID владельца, инвентарь сети и собранный трафик не должны попадать в репозиторий.

Перед ручной отправкой, обновлением или переносом БД остановите службу, после работы запустите снова. При переносе захватите `data/bot.lock`, выполните checkpoint WAL и используйте SQLite backup API: простое копирование `.sqlite3` при работающем писателе может потерять подтверждённые данные. Сравните строки, выполните `PRAGMA integrity_check`, измените только защищённый runtime.env и сохраните защищённую резервную копию до проверки. Для панели используйте каталог данных только для чтения, включая WAL/SHM, правильный UID и API `history.read_report(path, date, now)`; не создавайте пустую БД при ошибке чтения.

Автоматического удаления старых данных пока нет — следите за диском. Ошибки Telegram не сбрасывают расписание сборщика, но синхронный long polling и сетевые тайм-ауты могут задержать замер. Тесты используют только синтетические данные и не записывают их в рабочую БД. Панель и её развёртывание — отдельные компоненты; см. отдельную документацию при наличии.
